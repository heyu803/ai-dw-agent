# 二、技术选型与版本锁定

> 对应原方案第二章。本章是**面试重灾区**——面试官最爱问"为什么选 A 不选 B"。这里把核心组件清单和三个关键 ADR（架构决策记录）讲透。

## 2.2 选型决策记录（ADR）

> ADR（Architecture Decision Record）是记录"为什么做某个技术决策"的轻量文档。每条 ADR 通常包含：背景、候选项、决策、理由、权衡。

### ADR-001：LLM 选型 — Qwen2.5-Coder vs DeepSeek-V3

- **背景**：需要一个 SQL 生成能力强、中文友好的 LLM 作为 Agent 大脑。
- **候选**：
  - **Qwen2.5-Coder-32B（私有部署）**：代码/SQL 能力顶级，数据不出内网，但需要 GPU 资源。
  - **DeepSeek-V3（API 调用）**：价格极低、上下文长（128K）、免运维，但数据需出网。
- **决策**：**两者并存，按场景路由**。对数据敏感/高频的内部取数走私有 Qwen；对成本敏感/长上下文/低敏感场景走 DeepSeek API。
- **理由**：单一模型无法同时满足"数据安全 + 低成本 + 长上下文"，因此在 **LLM Gateway 层做多模型路由**（见第四章）。
- **权衡**：引入了路由复杂度和多模型一致性问题，需要 Prompt 在多模型上都验证过。

### ADR-002：Agent 框架 — LangGraph vs AutoGen vs CrewAI

- **背景**：Text-to-SQL 需要"生成→校验→失败重试→执行"的带环、带条件分支的流程控制。
- **候选**：
  - **LangGraph**：基于图的状态机，显式定义节点和条件边，**天然支持循环与条件分支**，状态可观测、可中断、可加人工介入。
  - **AutoGen**：以"多智能体对话"为核心抽象，擅长 Agent 间协作，但对"确定性流程控制"的表达不如状态机直观。
  - **CrewAI**：以"角色+任务"为抽象，上手快，但对复杂分支与精细状态控制的能力较弱。
- **决策**：选 **LangGraph**。
- **理由**：Text-to-SQL 的核心诉求是"**可控的、带重试环的流程**"而非"自由的多智能体对话"。LangGraph 的图模型能把"校验失败→带错误上下文重试→最多 N 次"这种逻辑用条件边显式表达，可读、可测、可观测。
- **权衡**：相比 CrewAI 上手稍陡，需要理解 State/Node/Edge 概念。

> 本项目 `src/agents/text_to_sql/graph.py` 就是一个最小但完整的 LangGraph 状态机实现，可直接对照学习。

### ADR-003：向量库 — Milvus vs Weaviate vs pgvector

- **背景**：RAG 知识库需要存储 Schema/文档的向量并做高性能相似检索。
- **候选**：
  - **Milvus**：专用向量数据库，**十亿级规模、混合检索、分布式高可用**，但部署运维较重。
  - **Weaviate**：自带模块化向量化与混合检索，开发体验好，社区活跃。
  - **pgvector**：PostgreSQL 插件，**复用现有 PG 运维**、事务一致性好，但超大规模性能与生态不如专用库。
- **决策**：大规模生产选 **Milvus**；如果向量规模不大且已有 PG，**pgvector 是性价比之选**。
- **理由**：本场景预期向量规模会随知识库增长到较大量级，且需要混合检索与高可用，Milvus 更匹配长期演进。
- **权衡**：Milvus 运维成本高，初期可先用 pgvector，规模增长后迁移。

> 本项目用内置 `BuiltinVectorStore`（内存余弦相似度）代替，`vector_store.py` 里保留了 `build_vector_store()` 工厂和 `milvus` 分支占位，体现"可平滑切换"的设计。

## 怎么把 ADR 讲好（面试技巧）

讲 ADR 不要只背"选了什么"，要讲出**决策框架**：
1. 先说**约束/诉求**（数据安全？成本？规模？流程可控性？）；
2. 再列**候选项各自的强弱**；
3. 然后给**决策**，并明确**这是基于哪个约束做的权衡**；
4. 最后补一句**这个决策的代价/未来演进路径**。

这样回答能体现你"懂权衡"，而不是"记住了答案"。
