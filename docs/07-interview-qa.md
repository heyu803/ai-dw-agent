# 面试问答宝典

> 把"会写代码"升级成"会讲清楚"。下面按模块整理高频面试题与参考答题思路。建议先能复述思路，再结合本项目的具体代码举例，效果最好。

---

## 一、整体与架构

**Q1：介绍一下你这个 AI 数仓 / Text-to-SQL 项目。**

参考思路（30 秒电梯版）：这是一个让业务同学用自然语言自助取数的系统。核心是一个基于 LangGraph 的 Text-to-SQL Agent：用户提问后，先 RAG 召回相关表，再做 Schema Linking 裁剪上下文，LLM 生成 SQL，经过语法/Schema/安全/语义/性能五层校验，校验失败会携带错误上下文让 LLM 自我修正（最多 2 次），通过后在只读沙箱执行并把结果总结成自然语言。另外还有一个数据质量 Agent 做规则检测、统计异常检测和基于血缘的根因分析。整套系统分五层（BFF/编排/AI 能力/数据/基础设施），LLM、向量库、数仓都用工厂模式做成可替换的。

**Q2：为什么 Text-to-SQL 要做成 Agent（状态机），而不是调一次 LLM？**

因为单次调用无法应对 LLM 生成 SQL 的各种问题：语法错、字段幻觉、危险操作、答非所问、性能炸裂。Agent 的价值在于**校验 + 自我修正的闭环**：生成→校验→失败带错误上下文重试→通过才执行。这需要状态、循环、条件分支，所以用 LangGraph 状态机表达最自然。

**Q3：你这套系统怎么保证可扩展、可替换？**

工厂模式 + 抽象接口。LLM 有 `LLMProvider` 抽象基类，mock 和 openai_compatible 是两个实现；向量库有 `build_vector_store()` 工厂；数仓走配置化的连接串。切换实现只改 `.env` 配置，不动业务代码。

## 二、LangGraph / Agent

**Q4：LangGraph 相比 AutoGen、CrewAI 的优势？**

LangGraph 以"图状态机"为核心抽象，**原生支持循环和条件分支**，适合"生成-校验-重试"这种确定性、可控的流程；AutoGen 强在多智能体对话协作；CrewAI 强在角色+任务的快速编排。Text-to-SQL 要的是"可控的带环流程"，所以选 LangGraph。

**Q5：（深入）你在 LangGraph 里踩过什么坑？**

路由函数（条件边的判断函数）里修改 state 不会被持久化。我一开始把 `retry_count += 1` 写在路由函数里，导致计数器永远是 0、无限重试触发 `GraphRecursionError`。正解是：路由函数只读 state 做决策，把"递增计数"放进一个专门的节点（`prepare_retry`），因为**只有节点对 state 的修改才会进入下一轮**。

**Q6：状态里都放了什么？为什么要有 trace？**

放了问题、改写问题、召回表、链接后的 schema、当前 SQL、五层校验结果、重试次数、执行结果、终态、以及 trace。trace 是每步的轨迹日志，用于**可观测性**——出问题时能回放"模型在哪一步生成了什么、为什么被拦"。

## 三、RAG / 检索

**Q7：Text-to-SQL 里 RAG 解决什么问题？**

解决"表太多塞不进 Prompt、且无关表干扰生成"的问题。先用 RAG 召回 Top-K 张最相关的表，只把这些表喂给 LLM，既省 token 又提准确率。

**Q8：什么是 RRF？为什么要用它？**

RRF（倒数排名融合）用来融合多路检索结果。公式 `score(d) = Σ 1/(k + rank_i(d))`，k 经验取 60。它的妙处是**只用排名不用原始分数**——因为向量相似度和 BM25 分数量纲不同，直接相加没意义；用排名就免去归一化，能鲁棒地融合异构检索器。生产里 RRF 之后还会接 Cross-Encoder 精排。

**Q9：向量检索和关键词检索为什么要混合？**

向量检索擅长语义相似但对精确关键词/专有名词不敏感；关键词检索（BM25）擅长精确匹配但对同义改写不敏感。两者互补，混合检索（hybrid search）+ RRF 融合能兼顾召回率和精确率。

**Q10：Embedding 模型怎么选？**

中英混合场景常选 BGE-M3（多语言、多粒度、1024 维）。要点：维度、语言覆盖、领域适配（必要时微调）、推理成本。本项目用了一个字符 n-gram 哈希的轻量替身，仅为零依赖演示，生产必须换真模型。

## 四、Text-to-SQL 校验（高频深挖）

**Q11：你的五层校验分别是什么？**

语法（sqlglot 能否解析，ERROR）、Schema（表/列是否真实存在，防幻觉，ERROR）、安全（是否只读、禁 DROP/DELETE，BLOCKER）、语义（LLM 判断是否答对问题，WARN）、性能（SELECT \*/缺 LIMIT/缺分区，WARN）。设计原则是**由轻到重、由确定到模糊**，确定性强的（语法/安全）放前面，模糊的（语义）靠 LLM 判断且只告警不阻断。

**Q12：安全校验为什么不能只用正则？**

正则能快速拦截危险关键词，但容易被绕过（注释、大小写变体、字符串里的关键词）。所以再加 AST 兜底：解析后判断根节点类型，**只允许 SELECT/UNION/子查询**，其它一律拦截。正则保证快，AST 保证准，双重判定。

**Q13：Schema 校验怎么避免把别名误判为不存在的字段？**

`SELECT SUM(x) AS total` 里的 total 是别名不是真实列。先用 `find_all(exp.Alias)` 收集所有别名，校验列时把别名排除，只校验真正引用的物理列是否存在。

**Q14：校验失败怎么重试？**

ERROR 级别（语法/Schema）可重试：用 `sql_fix` Prompt 把"上一版 SQL + 具体校验错误"一起喂回 LLM 让它修正，最多 N 次（默认 2）。BLOCKER（安全）不重试直接拦截。WARN 不阻断。重试耗尽则返回错误。

**Q15：只读沙箱怎么实现的？为什么还要它，校验不是已经拦了吗？**

沙箱用 SQLite 的 `mode=ro` 只读连接 + 自动注入 LIMIT。**纵深防御**思想：校验层防"生成危险 SQL"，执行层防"万一漏过也执行不了"。安全要多层，不赌单点不出错。生产里换成数仓只读账号 + 超时 + 行数上限 + 资源队列。

## 五、LLM Gateway / Prompt

**Q16：为什么要做 LLM Gateway？**

统一模型调用入口，做多模型路由（按任务/成本/上下文/数据敏感度选模型）、降级容灾（主备多活）、限流熔断、Token 计费、调用链埋点。把"用哪个模型、怎么容灾"和业务逻辑解耦。

**Q17：Prompt 为什么要版本管理？**

Prompt 是 Agent 的"源代码"，效果对它极敏感，必须能灰度、回滚、A/B、审计。每次调用记录用的是哪一版 Prompt，出问题能回溯。本质是"Prompt 也要 CI/CD"。

**Q18：私有模型 vs API 模型怎么选？**

数据敏感/高频走私有部署（Qwen2.5-Coder，数据不出网）；成本敏感/长上下文/低敏感走 API（DeepSeek-V3，便宜、128K 上下文）。所以才需要 Gateway 做多模型路由，而不是二选一。

## 六、数据质量

**Q19：数据质量怎么做？**

三个层次：① 规则检测（not_null/unique/range 等硬规则）；② 统计异常检测（Z-Score/IQR/Prophet 抓软异常）；③ 根因分析（结合血缘追溯定位问题源头）。

**Q20：Z-Score 和 IQR 怎么选？**

数据近似正态用 Z-Score；但 Z-Score 对极端值敏感（离群点会污染均值方差），有离群点干扰时用 IQR（基于分位数，更鲁棒）。有明显周期性的时序用 Prophet。

**Q21：根因分析的核心思路？**

数据异常会沿血缘从上游向下游传导。所以发现下游异常后，沿血缘链往上游逐个做质量探针，定位到最上游的异常点就是根因；若上游全正常，则异常源于本表 ETL 或真实业务波动。血缘用 Neo4j 存储和查询。

## 七、加分项 / 开放题

**Q22：这套系统怎么保证 Text-to-SQL 的准确率？怎么评估？**

多管齐下：精准的 RAG 召回 + Schema Linking 降低上下文噪声；五层校验 + 重试兜底；Prompt 调优。评估上建一个"问题→标准 SQL/标准结果"的测试集，算执行准确率（execution accuracy，结果是否一致）和 SQL 匹配率，回归测试每次 Prompt/模型变更。

**Q23：如果数仓有几千张表，RAG 召回不准怎么办？**

分层召回：先按业务域/主题粗筛，再在域内做向量+关键词混合检索；给表和字段写高质量的业务注释（喂给 embedding）；引入查询历史/热度做先验；必要时对召回结果做 Cross-Encoder 精排；还可以让用户在不确定时做澄清式追问。

**Q24：这个项目还能怎么演进？**

接真实 LLM 和 Milvus/Neo4j；加多轮对话与指代消解；加结果缓存与查询热度学习；加人工介入（HITL）让用户确认高风险查询；加可观测性（Prometheus 指标、调用链）；把校验做成可配置规则引擎；Text-to-SQL 扩展到 Text-to-Chart、自动报表。
